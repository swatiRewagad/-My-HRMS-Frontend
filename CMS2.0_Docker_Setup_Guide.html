The real full-stack setup, corrected and completed

Your existing cms-infra Docker Compose stack — MySQL, Redis, Kafka, OpenSearch, Keycloak, thirteen backend microservices — with two things added: cms-mail-intake (embedded SMTP) and cms-portal-frontend (the CRPC/OCR-test UI, since the stack's own frontend doesn't have those screens). Keycloak now provisions itself — no manual clicking through the admin console.

Corrected from the previous version of this document

  • Database is MySQL on port 3306 (the original cms-infra/docker-compose.yml uses Oracle on 1521 instead — this stack replaces it entirely). cms-infra/mysql/init.sql exists in the repo but isn't referenced by this compose file; Hibernate's dev-local profile creates the schema automatically.
  • Oracle is replaced with MySQL entirely — docker-compose.mysql.yml is a full standalone stack, not an add-on to the Oracle-based file. cms-backend runs its dev-local Spring profile (the one actually verified against MySQL — the default prod profile hardcodes an Oracle Hibernate dialect and would connect to MySQL fine, then fail on every query).
  • CMS_CORS_ALLOWED_ORIGINS in .env is silently ignored — cms-backend actually reads CMS_CORS_ORIGINS (no "ALLOWED"). Harmless here since the built-in default already covers localhost:4200, but worth knowing if you change origins later.
  • The routes the old doc told you to test (/crpc, /crpc/reviewer, /admin/dashboard) belong to cms-portal-frontend, not the cms-frontend this stack actually builds at http://localhost — that one only has five routes (public complaint filing, tracking, physical-complaint). Section 02 adds cms-portal-frontend as its own container specifically to fix this.
  • The Keycloak client is cms-frontend, not cms-portal or cms-portal-frontend — keycloak-auth.service.ts hardcodes that client ID regardless of which Angular app is actually running. One client, both apps.

Known bugs in the application itself — not fixable from a setup doc

  • Two incompatible Keycloak realms are wired into running code. cms-mail-intake and cms-assignment-service (plus the frontend's default, non-Docker environment.ts) expect realm rbi-cms; cms-backend, cms-api-gateway, and cms-frontend expect realm cms. This stack standardises on cms and overrides cms-mail-intake's issuer-uri to match — cms-assignment-service is left as-is since nothing in this stack's gateway routes to it anyway.
  • CEPC role names don't match between frontend and backend. The backend's @CepcRoleGuard requires prefixed roles (CEPC_DO, CEPC_REVIEWER...); the frontend's own role-check code checks bare names (DO, REVIEWER, INCHARGE, CA, CP). The realm import gives CEPC test users both forms so testing isn't blocked, but expect inconsistent behaviour on CEPC screens until this is fixed in code.

Prerequisites

Docker Desktop only — every service builds its own image from source; nothing else needs installing on your laptop.

  • Docker Desktop, running, with at least 10 GB RAM allocated (Settings → Resources — this stack is genuinely heavy: MySQL, Kafka, OpenSearch, two backend replicas, and now two frontends)
  • Ports free: 80, 3306, 4200, 6380, 8080, 8082, 8090, 8092, 8100, 8180, 9090, 9200, 2525, 3000, 29092
01

One-time configuration

Two edits before your first build — both are about telling the stack where your real external OCR service lives.

1. cms-infra/.env

cms-infra/.env
# Your real OCR service — cms-backend calls this server-to-server
OCR_EXTERNAL_URL=http://your-ocr-host:8000

# Optional — only needed if you also want the Groq fallback provider active
# GROQ_API_KEY=gsk_...

2. cms-portal-frontend's OCR URL (browser-side, so it's baked in at build time)

The "AI Extract" button on the physical-letter screen calls your OCR service directly from the browser, separately from cms-backend's own server-side call — Angular can't read a .env file at runtime, so this one line needs editing before you build the image:

cms-portal-frontend/src/environments/environment.docker-local.ts
  ocrServiceUrl: 'http://your-ocr-host:8000',  // same address as OCR_EXTERNAL_URL above

How the 12 microservices actually get built

Each one has its own build: block in docker-compose.mysql.yml, pointing at the same shared Dockerfile — cms-infra/Dockerfile.microservice — with a different SERVICE_NAME build argument per service, e.g.:

docker-compose.mysql.yml — one of the 12, as an example
cms-workflow-service:
  build:
    context: ..                              # repo root — so Maven can see cms-workflow-service's own pom.xml
    dockerfile: cms-infra/Dockerfile.microservice
    args:
      SERVICE_NAME: cms-workflow-service       # tells the shared Dockerfile which module to mvn package

So docker compose ... --build runs that shared Dockerfile 12 separate times, once per SERVICE_NAME — each one is a real, independent mvn package against that microservice's own source under CMS2.0/<service-name>/, not a shortcut or a shared skip. You'll see all 12 names scroll by in the build output as separate build stages.

What got added, and why

Four new files, all additive — nothing in the original cms-infra/docker-compose.yml was changed.

FileWhat it does
docker-compose.mysql.ymlFull standalone stack (29 services, including nginx and every microservice from the original file) — MySQL instead of Oracle, plus cms-mail-intake, cms-portal-frontend, and cms-mock-ocr-api added, cms-backend's OCR chain forced onto that mock (or your real provider once configured), and Keycloak's realm auto-import turned on. Run this file alone — nothing else needed.
keycloak/cms-realm.jsonEverything the old doc's "click through the admin console" section asked for — realm cms, all 10 original roles plus MAIL_INTAKE_ADMIN, and the same test users — as data Keycloak imports on first boot.
cms-mail-intake/DockerfileDidn't exist before. This module depends on a sibling Maven module (cms-common) that isn't published anywhere, so its build context is the whole repo, not just its own folder.
environment.docker-local.ts + an angular.json build configcms-portal-frontend's existing environment files all pointed somewhere else (dev server ports, or relative OpenShift-proxied paths) — this one points at what this specific stack actually publishes.
Two property overrides worth understanding ▸

cms-backend's OCR chain is forced via command-line arguments (--cms.ocr.chain=external --cms.ocr.external-url=...), not environment variables — because cms.ocr.external-url has no placeholder in either application.yml to bind an env var to. Command-line args always win regardless, so this works no matter what profile is active.

cms-mail-intake's SMTP allowlist defaults to 127.0.0.1 only. Docker NATs a host-side SMTP client through the bridge network, so it arrives as a 172.x address — CMS_MAIL_INTAKE_ALLOWLIST_CIDRS widens that to cover it.

Keycloak, and cms-mail-intake's admin API

Get a real access token for one of the imported MAIL_INTAKE_ADMIN users, then use it against the admin endpoints:

terminal
TOKEN=$(curl -s -d "grant_type=password&client_id=admin-cli&username=mail-intake-admin&password=Test@123" \
  http://localhost:8180/realms/cms/protocol/openid-connect/token | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

curl -H "Authorization: Bearer $TOKEN" \
  http://localhost:8092/cms-mail-intake/admin/mail-intake/quarantined

To test the maker-checker replay flow properly, request a replay as mail-intake-admin and approve it as mail-intake-checker (get a second token for that user) — the service rejects a self-approval on purpose.

06

Troubleshooting

Keycloak didn't import the realm

--import-realm only imports on a genuinely fresh database — if cms-keycloak-db's volume already has data from a previous run (before this realm file existed), it skips the import silently. Reset just that piece:

terminal
docker compose -f docker-compose.mysql.yml down
docker volume ls | grep keycloak-db   # confirm the exact name first — project-name prefixed
docker volume rm cms-infra_cms-keycloak-db-data
docker compose -f docker-compose.mysql.yml up -d --build

cms-mail-intake build fails resolving cms-common

Confirm you're running docker compose from cms-infra/, not from inside cms-mail-intake/ — the extras file sets this service's build context to the repo root specifically so Maven can see the sibling cms-common module.

cms-backend keeps restarting, can't reach MySQL

Check docker compose logs cms-mysql for ready for connections — MySQL usually starts faster than the old Oracle setup did, but a slow first boot can still race the backend's connection attempt. Once MySQL is healthy: docker compose restart cms-backend-1 cms-backend-2.

401/403 calling the mail-intake admin API

Token expired (30 minutes) — get a fresh one with the same curl command. Wrong role — only mail-intake-admin and mail-intake-checker carry MAIL_INTAKE_ADMIN.

SMTP connection refused or rejected

Refused: docker compose ps should show cms-mail-intake healthy; check nothing else on your laptop holds port 2525. Rejected: the CIDR override didn't take — check the container's actual startup log for the allowlist it loaded.

OCR response looks right but form fields stay blank

The frontend only reads a fixed set of field names out of the response envelope. A field your real OCR service doesn't return just leaves that form field untouched — not an error.

Port already in use

Something on your laptop already holds one of the ports listed in Prerequisites — most commonly a native Oracle/MySQL install, or a previous native run of one of these services outside Docker.
