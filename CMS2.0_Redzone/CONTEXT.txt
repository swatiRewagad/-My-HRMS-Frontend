		CMS 2.0 is a microservices-based complaint management system for RBI (Reserve Bank of India) under the Integrated Ombudsman Scheme. It handles the full lifecycle of banking complaints: filing, eligibility check, assignment, workflow processing, SLA monitoring, appeals, and final orders.

	<Kafka Topics (Outbox Pattern)>
		complaint.ingested    -> New complaint created
		complaint.assigned    -> Officer assigned
		complaint.inprogress  -> Work started
		complaint.escalated   -> SLA breach / manual escalation
		complaint.resolved    -> Resolution provided
		complaint.closed      -> Final closure
		complaint.dlq         -> Dead letter (permanently failed)

		Flow: Service writes to OUTBOX_EVENTS table -> cms-outbox-publisher polls (5s interval, max 5 retries) -> publishes to Kafka topic -> marks as PUBLISHED.
	</Kafka Topics>

	<Complaint Status Lifecycle>
		ComplaintStatus enum (cms-common): NEW, ASSIGNED, IN_PROGRESS, UNDER_REVIEW, ESCALATED, RESOLVED, CLOSED, APPROVED, REJECTED, SENT_BACK

		Public Portal Flow:
		  Citizen login (OTP) -> Eligibility wizard -> File complaint -> Track/Withdraw/Appeal/Feedback

		CRPC Flow (mail intake):
		  Email ingestion -> OCR extraction -> DEO assessment -> Reviewer verification -> Auto-closure or forwarding

		RBIO Flow:
		  NEW -> ASSIGNED (round-robin) -> IN_PROGRESS (officer) -> UNDER_REVIEW (supervisor) -> Advisory/Notice 13(1) -> Conciliation -> Adjudication -> CLOSED

		CEPC Flow:
		  NEW -> ASSIGNED (DO) -> IN_PROGRESS -> REVIEWER -> IN_CHARGE -> Closing Authority -> CLOSED (with conciliation/adjudication dates)

		RE Portal Flow:
		  Complaint forwarded -> RE views complaint -> RE responds -> Response tracked (ReResponseTracker)

		AA (Appeal) Flow:
		  Appeal filed (within 30/60 days of closure) -> AA_REGISTRAR -> AA_BENCH_OFFICER -> AA_AUTHORITY -> Order issued
	</Complaint Status Lifecycle>

<ARCHITECTURAL CONSTRAINTS>
	<Security>
		1. Keycloak SSO for all staff portals (CEPC, RBIO, RE, AA, CRPC, Admin). OTP-based auth for citizen portal.
		2. PII Encryption: CMS_ENCRYPTION_SECRET env var required (min 16 chars). EncryptionKeyService handles AES encryption of sensitive fields.
		3. Anti-Automation: Velocity checks (configurable threshold), minimum form submission time, standard header validation, captcha enforcement.
		4. Rate Limiting: configurable per-endpoint (complaints-per-minute, api-requests-per-second) via RateLimitFilter.
		5. CORS: strict allowed-origins list (localhost:4200, 4201, 4202, 4300).
		6. Input Validation: File upload validation (type, size), character limits on all text fields, parameterized queries (JPA/Hibernate).
		7. Role-based access control: AOP-based @RbioRoleGuard, @CepcRoleGuard, @AaRoleGuard, @ReRoleGuard annotations on service methods.
	</Security>

	<Performance>
		1. Hazelcast embedded cache for frequently accessed data.
		2. Async file uploads with chunked upload support (5MB chunks, max 50MB per file).
		3. Database indexing on complaint number, status, priority, email, category, bank, created_at, triage signal, maintainability.
		4. Kafka transactional outbox pattern for reliable async event processing.
		5. Connection pooling via HikariCP (configurable pool size).
		6. WebSocket support for real-time notifications (WebSocketConfig, STOMP broker).
	</Performance>

	<Non-Functional Requirements>
		NFR-005: 15-minute session timeout for citizen portal.
		NFR-006: File upload limits (2MB per file, 25MB total, 10 files max) per EAAP guidelines.
		NFR-007: Max 6 concurrent requests.
		NFR-008: 7-year data retention policy.
		NFR-015: Integration endpoints (EKAMEV, CDR, SIEM, SMS Gateway, SMTP).
	</Non-Functional Requirements>
</ARCHITECTURAL CONSTRAINTS>
