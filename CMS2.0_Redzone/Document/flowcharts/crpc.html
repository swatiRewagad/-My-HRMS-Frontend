CRPC — Centralised Receipt & Processing Centre

How an email, a scanned letter or a phone call becomes a formal complaint on the system

Written for business readers · every step below is what the software does today Prepared from the CMS 2.0 source code, 30 Sep 2026

In one paragraph

Not every grievance arrives through the portal. Emails land in a shared inbox, physical letters are scanned, and the helpdesk takes calls. CRPC is the single front door for all of those. Incoming items are first filtered automatically — junk is dropped, duplicates are attached to the original case, and anything the system cannot read is set aside for manual typing. What survives becomes a draft, assigned in rotation to a Data Entry Operator who reads the document and keys in the complaint details. A Reviewer then decides: approve it (which creates a real complaint and sends it to the right office), send it back for correction, or mark it as not a complaint at all.

1. Who does what

RoleWhat this person does in the system
Data Entry OperatorReads the incoming email or scanned letter and keys the complaint details into a draft. Corrects whatever the automatic text reading got wrong, then sends the draft for review.

CRPC In-chargeSupervises the queues and workload.

Helpdesk (toll-free)Logs grievances received over the phone.
AdministratorCan reopen a draft that was closed as "not a complaint".

3. The same journey as a checklist

  1. System Filter the incoming item. Four checks in order: was RBI only copied in, is the sender on the ignore list, have we seen this exact message before, and is it a repeat of something already closed.
  2. System Try to read the document. The language is detected first; if it is a regional language or the confidence is low, automatic reading is skipped entirely and the item goes to the manual queue. Otherwise text is extracted and the draft is handed to the next operator in rotation.
  3. Data Entry Operator Key in the complaint. Whatever the operator types wins over what was read automatically.
  4. Data Entry Operator Send to the Reviewer.
  5. Reviewer Approve, send back, or reject. Approving is the only path that creates a real complaint.
  6. System Create and route the complaint. A reference number is generated and the case is placed with either an Ombudsman office or the consumer protection cell, based on which institution is complained about.

Two limitations 1. These are reminders only. None of them moves, escalates or reassigns a draft — a person must still act.
2. The overflow re-routing never fires. It looks for drafts in a state the live system never writes, so it always finds nothing. Reviewer queues are effectively not balanced automatically.

5. Things to know before relying on this

What you might assumeWhat the code actually does
"Only a Reviewer can approve a draft" There is no role check at all on the screen that drives drafts. Any signed-in CRPC staff member can move any draft to any state, including approving it and creating a complaint.
"A draft has to follow the proper order" There is no order check either. A draft can jump straight from newly-arrived to approved.
"There is a rulebook enforcing the draft lifecycle" There is one — with proper role and order checks — but no screen uses it. It is unreachable code. The live screens use a different, unguarded path.
"'Sent back' and 'Not a complaint' are official states" They are not on the official list. The screens write them anyway and they are stored as-is, so reports built on the official list will not see these drafts.
"If something goes wrong the screen shows an error" The intake service reports failures as successes with an error message buried inside. A draft that could not be found, or an upload that failed, looks like a normal response — the screen's error handling never triggers.
"Scanning reads regional-language letters" Language is detected before reading is attempted, and regional-language items skip automatic reading entirely. They land in the manual-typing queue by design.
Technical appendix — for developers and testers

Two disjoint state machines; the authoritative-looking one is dead

Vocabulary A — CrpcWorkflowService (DEAD)

NEW_COMPLAINT, SENT_FOR_APPROVAL, APPROVED, SENT_BACK, NOT_A_COMPLAINT

  • Enum backing: none, bare string literals
  • Transition guard: yes — VALID_TRANSITIONS (lines 27–33) via validateTransition (176–182)
  • Role guard: yes — @PreAuthorize
  • Frontend callers: zero in components/crpc/
  • Reachable only via /api/v1/crpc/workflow/*

Vocabulary B — EmailSyndicationApiController (LIVE)

DRAFT → PENDING_MANUAL_ENTRY → ASSIGNED → IN_PROGRESS → SENT_TO_REVIEWER → APPROVED_ROUTED → CONVERTED; terminals DUPLICATE, IGNORED, REJECTED

  • Enum backing: entity/DraftStatus.java
  • Transition guard: none
  • Role guard: none beyond the coarse STAFF_ROLES URL grant (SecurityConfig.java:187)
  • Frontend callers: all screens

Every live edge is the same call — PUT /api/v1/email-syndication/drafts/{draftId} — with a different status string in the body, written verbatim at :765.

Off-enum values the frontend writes

SENT_BACK_TO_DEO and CLOSED_NOT_A_COMPLAINT (reviewer-assessment.component.ts:401-402) persist unvalidated. DraftStatus.OPEN = {ASSIGNED, IN_PROGRESS, SENT_TO_REVIEWER, DRAFT, PENDING_MANUAL_ENTRY} and therefore excludes both.

Intake gates, in order

CC/BCC-only ⇒ NON_COMPLAINT auto-closed · ignore-list (:186) ⇒ IGNORED · messageId idempotency ⇒ existing draft returned · duplicate-of-CLOSED-parent (:984) ⇒ DUPLICATE with email and attachment linked to the parent · language detection runs before OCR and gates it ⇒ PENDING_MANUAL_ENTRY (:372, :620).

Exit

APPROVED_ROUTED (:787) triggers createComplaintFromDraft (:794): status='assigned', stage='INITIAL_REVIEW', number CMP-yyyyMMdd-######, timeline CREATED_FROM_CRPC by REVIEWER. Routing via routingService.resolveDepartment(entityName), overridden by a targetOffice prefix: RBIO* ⇒ dept RBIO / role RBIO_OFFICER; CEPC* ⇒ dept CEPC / role CEPC_DO.

The only real role guard

POST /crpc/drafts/{id}/reopen — @PreAuthorize("hasRole('ADMIN')") (CrpcDraftEnhancementController:85-93). CRPC_ROLES = {CRPC_HEAD, CRPC_ADMIN, CRPC_INCHARGE, DEO, REVIEWER, ADMIN} (SecurityConfig.java:65-67). DEO and REVIEWER routes are themselves unguarded (app.routes.ts:258-280). CRPC_DEO / CRPC_REVIEWER appear in @PreAuthorize on the dead controller but are not in CRPC_ROLES.
