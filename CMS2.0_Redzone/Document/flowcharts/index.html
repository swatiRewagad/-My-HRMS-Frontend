How the RBI complaint management system actually works today, module by module

How to read these pages

Each page describes one part of the system: who does what, a flowchart of the journey, the same journey as a numbered checklist, the deadlines that apply, and a section called "Things to know before relying on this" that sets out where the software behaves differently from what you would reasonably expect. At the bottom of every page there is a collapsed technical appendix with file names, status values and API details — open it only if you need it.

Everything here is derived from reading the code, not from earlier documentation. Where the code and the written requirements disagree, these pages describe the code.

The three things to know before reading any of it

1 · These are six separate systems, not one workflow Each module has its own set of states, its own rules and its own degree of enforcement, while all of them write to the same complaint record. A complaint's "status" means something different depending on which module last touched it.
2 · Enforcement varies enormously between modules The Appellate Authority and the bank portal genuinely check who is asking and whether the action is allowed right now. The Ombudsman office checks partially. The consumer protection cell and the central intake centre check almost nothing — the screens decide what to show, and the server accepts whatever it is sent.
3 · Almost nothing happens on a timer Only the bank's 15-day reply clock is actively enforced. Inside the RBI offices, deadlines are calculated and displayed but never acted on. No case escalates, reassigns or closes by itself.
