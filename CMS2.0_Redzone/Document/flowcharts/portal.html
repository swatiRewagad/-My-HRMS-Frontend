Citizen Portal — filing and tracking a complaint

What a member of the public goes through, from logging in to watching their case progress

Written for business readers · every step below is what the software does today Prepared from the CMS 2.0 source code, 30 Sep 2026

In one paragraph

A citizen signs in with their mobile number and a one-time password — there is no username, no password and no anonymous filing. Before they are allowed to type a single complaint detail, the portal runs an eligibility interview: a set of yes/no questions that establish whether the Ombudsman may hear this grievance at all. Failing a question ends the journey there with an explanation. Passing it opens a six-step form. On submission the citizen gets a reference number immediately, and can come back at any time — even without logging in — to see one of four plain-language stages.

1. Getting in

  1. Enter a 10-digit Indian mobile number. It must begin with 6, 7, 8 or 9.
  2. Solve a CAPTCHA. Either a picture code or, for accessibility, an audio arithmetic question.
  3. Agree to the consent statement. Filing cannot proceed without it.
  4. Receive and enter the one-time password. It is valid for five minutes.
  5. You are in for 15 minutes of inactivity. After that the session drops and you sign in again.
Rate limits, in the order they are applied The portal refuses an OTP request if: the number is malformed · the number is inside a cool-off period after too many attempts · the CAPTCHA is wrong · the hourly request limit for that number is used up · or a previous code was requested too recently. Each gives a distinct message.
Tracking does not need a login Anyone holding a reference number can look up a case's stage without signing in. Filing, however, always requires the OTP login.

3. The time limits the portal enforces

30 daysthe bank gets this long to reply before you may come to the Ombudsman
310 dayswindow to approach the Ombudsman when the bank never replied
90 dayswindow to approach the Ombudsman after the bank's reply or rejection
5 minutesvalidity of the login OTP
15 minutesidle time before the session ends

All of these come from the server, not the browser, so they cannot be bypassed by editing the page. The same limits are re-checked on submission even if the interview was passed earlier.

Two behaviours to expect support calls about 1. Stages can go backwards. A case that was "With the bank" can return to "Under review by RBI".
2. Unrecognised situations show as Stage 1. Many genuine internal states — conciliation, formal notice, awaiting documents, and the whole consumer-protection-cell review chain — are not in the citizen mapping, so those citizens see "Registered" even though real work is under way.

5. Features that look present but do not work

What the screen offersWhat actually happens
Attaching documents during the eligibility interview The upload is validated and marked mandatory, but the files are never sent to the server. They are silently lost when the complaint is submitted.
Adding an attachment to an existing complaint The endpoint the screen calls does not exist on the server.
Listing your complaints by mobile number Also calls a route that does not exist.
The "not maintainable" outcome reference A reference number is shown to the citizen but nothing is stored — it cannot be looked up later.
An older eligibility check screen Still reachable and carries a hard-coded 365-day limit that contradicts the live rules. It is not part of the current journey.
Automatic routing on registration It runs, but if it fails the error is swallowed — the complaint is still registered, just possibly unrouted.
Technical appendix — for developers and testers

Routes and guards

Declared in app.routes.ts:400-425. /public/file-complaint sits behind publicAuthGuard — no anonymous filing. Tracking by reference number is open.

Authentication

Mobile pattern ^[6-9]\d{9}$ + CAPTCHA (VISUAL image or MATH audio) + consent → POST /api/v1/citizen/auth/send-otp. Gate order: mobile present → format → cool-off (429) → CAPTCHA → hourly limit → resend cooldown. Then POST …/verify-otp; token held in sessionStorage and sent as X-Citizen-Token. OTP window 300s in every profile; idle timeout 15 min.

Two-phase wizard

phase = signal<'eligibility'|'form'|'success'|'non-maintainable'>. Phase A reads 14 questions from EligibilityQuestionMasterSeeder, filtered by applicableEntityType (ALL/RBIO/CEPC/NON_CEPC) so the step count is dynamic. Block clauses: 10(1)(j), 10(2)(b)(ii), 10(2)(a), 10(1)(g). Phase B is fixed at six steps. Forward navigation guarded by goToStep(n) only when n <= highestStepReached().

Submission

check-duplicate fails closed. Windows (RE 30d, grievance 310d, filing 90d) are server-served and re-asserted in ComplaintApiV1Controller.filingWindowRefusal(). POST /api/v1/complaints → 201, status REGISTERED, slaDueDate = +30d. IntakeTriageService.triageOnRegistration runs next with exceptions swallowed.

Citizen stage mapping

CitizenStageMapper: 1 = pending,new · 2 = assigned,in_progress,under_review,escalated · 3 = approved,sent_back · 4 = resolved,rejected,closed,withdrawn; unknown ⇒ 1. Not monotonic.

Confirmed dead ends

  • POST /complaints/{id}/attachments — no server mapping.
  • GET /complaints/by-phone/{phone} — no server mapping.
  • Eligibility-phase uploads: payload build at lines 2158–2196 contains no multipart part.
  • Orphaned wizard-check with a contradictory hard-coded 365-day rule.
  • Non-maintainable reference NM-<timestamp> is never persisted.
  • A second, duplicate eligibility-wizard implementation still exists in the tree.
